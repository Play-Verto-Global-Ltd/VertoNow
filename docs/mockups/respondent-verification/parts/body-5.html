Spec

What each board implies in code, what it costs, and the things this deck deliberately does not do. Everything below was read out of the tree at 817d3a9 (14 Sep 19:31); line references are to that commit.

  1. 1
    The token, and why there is no migration.

    Player already carries email_verified_at and an idempotent verify_email! that only writes when the column is nil. What it lacks is a token purpose and a send. Add generates_token_for :email_confirmation, expires_in: 7.days { email_address }, mirroring User line-for-line — keyed on the address, so that changing the address invalidates any outstanding link, which is the property that makes a stale token harmless.

    7 days, not the 20 minutes a sign-in link gets. The two are different kinds of thing: a PlayerSignInLink is a bearer credential stored as a digest in its own table, and is sized like one. This token grants nothing — spending it sets a timestamp — so it is sized for how long a real inbox takes to get read. No migration, no new table, no schema change.

    One document has to move with it. docs/DATA_RETENTION.md states as property 4 that "every credential is single-use, a digest, or somebody else's", and enumerates the three. A generates_token_for token is none of them — it is reusable until it expires, never stored, and ours. That is the right trade for a token that grants nothing, but the property as written becomes false and has to be rewritten rather than quietly outgrown.

  2. 2
    The gate already exists and is already firing.

    This is the fact that makes the whole change small. PlayerAudience.for_survey has filtered on where.not(email_verified_at: nil) since it was written, and deliverable? applies the same rule per-send so nothing leaks past the scope. Nothing needs building to enforce verification. The gate is correct, it is live, and it is silently excluding every password-signup respondent in the database.

    So §1 is not "add a gate". It is "give the people already behind the gate a way through it".

  3. 3
    Why nothing else gets gated.

    The creator gate sits on publishing because an unproven creator can collect other people's birth dates and locations under an address its owner never consented to. The respondent case has no equivalent: an unproven respondent holds only their own answers. The only thing their address is evidence for is whether we may write to it, so that is the only thing it gates.

    Claims, results, the wallet, comparison, the account itself — all stay open. A gate on any of them would cost conversion on the exact card that exists to win it, and would protect nothing. CLAUDE.md's note that SMTP is optional in this deployment is the second reason: a gate on anything load-bearing would mean a misconfigured mail server locking respondents out of their own answers.

  4. 4
    The resend, and not building an oracle.

    The resend lives on /you and /you/account, behind a signed-in player session, and takes no address parameter — it can only ever mail the account you are already inside. That is what keeps it from being either an enumeration oracle or a mail-bomb button, and it is a materially different threat model from PlayerController#join, which accepts an address from an anonymous caller.

    Rate-limited at 5 per 10 minutes, matching the creator's. The confirm landing page carries no resend and echoes no address beyond what the token resolves.

  5. 5
    Copy the respondent mailer, not the creator's.

    PlayerSignInMailer is the file to copy, and specifically not EmailConfirmationsMailer — the creator's is older and hardcodes English with no I18n.with_locale. The respondent one already carries the two things this mail needs:

    I18n.with_locale(SupportedLocales.coerce(player.preferred_locale)), because a mailer runs in a Solid Queue job with no request and therefore no Current.locale — without it the mail renders in whatever locale the worker was last left in. And headers["X-Entity-Ref-ID"] = SecureRandom.uuid, so a resend does not stack under the original in a mail client and get missed.

    Subject names the organisation. HTML and text parts both. Delivery wrapped the way EmailConfirmationsController.deliver wraps it — rescue, report, return nil — because the account has already been created and persisted by the time this runs, and a mail failure must never turn a completed signup into an error.

    Two calls a builder will hit, settled here. Honour EmailSuppression. The sibling transactional mail does not check it, but that table carries hard bounces and complaints — sending a confirmation to an address that has already bounced achieves nothing and spends sender reputation to do it. Skip the send, leave the account unverified, and let the banner say so. No welcome mail on confirmation. The creator flow sends one; a respondent has had the account since the end of the Verto and the landing page already says what changed, so a second mail would be a notification about a notification.

    And it must degrade when SMTP is unconfigured, which this deployment allows. The pattern already exists: MailConfigCheck.deliverable? (lib/, not app/lib/), used at PlayerSessionsController — when mail cannot go out, do not mint the token and do not promise the mail. The card's new sentence has to be conditional on the same check, or it promises an email that a misconfigured deploy will never send.

    And it must carry ?locale=, which no emailed link does today. #join_google already puts it in the URL on purpose — "where resolve_locale's ?locale= already means the pages in between are drawn in it too". #join and PlayerSignInMailer do not. So a mail rendered in the respondent's language currently opens a page in the browser's, and a verification mail that copies the mailer verbatim inherits that. Put the locale in the link.

    With a trap in the testing of it. deliverable? opens return true unless ActionMailer::Base.delivery_method == :smtp, and delivery_method is :test in test and not :smtp in development — so it is unconditionally true in both, and the pessimistic branch is unreachable locally without stubbing. test/integration/player_password_sign_in_test.rb already stubs it exactly for this, and the new copy's test copies that.

  6. 6
    The Google door: what is constraint and what is choice.

    Constraint (real, not negotiable cheaply). OmniAuth's request phase is a CSRF-protected POST — allowed_request_methods = [:post] plus request_validation_phase = TokenVerifier.new — and Rails 8.1 binds the CSRF token to the session. The card cannot produce a token that validates, for a reason stronger than the controller's own comment gives: cached_play_page caches the /play/:token HTML as shared bytes keyed on link + deck version + locale, so for most respondents that page's token was minted during a stranger's request. The Service Worker cache is a second, independent reason. A direct POST would fail for nearly everyone.

    Choice (reversible). That the interstitial does not auto-submit is a separate decision, stated as such in the controller: a Back-button trap, and a dislike of a GET that starts a redirect when a scanner touches it. The scanner half is weak here by the controller's own later admission — "nothing is spent here", and a test asserts it. The Back-button trap is real and is what the auto-submit has to guard against.

    And there is a third thing, which is neither constraint nor architecture: the two buttons are the same string. _join_block.html.erb and player_joins/show.html.erb both render t("auth.social_continue"), so the respondent presses "Continue with Google" and arrives at a page whose button is also "Continue with Google". The step reads as a no-op because it is labelled as one.

    Recommended, in this order: (1) give the second button its own key — one new string, one view line, no controller and no test rewrite, and it addresses the complaint as reported. (2) Then, if the step still reads as friction, auto-submit, guarded against back_forward navigations with the button left in place for that case and for no-JS. Doing it in that order means the risky half is only paid for if the cheap half does not settle it.

    One correction worth recording, because it narrows option 3. "The handoff response cannot carry a live CSRF token" is true of today's wiring, not of what is possible: a token minted on an earlier request in the same browser does validate on a later POST to /auth/google_player. What blocks it is one line — :join_google sitting in the null_session list, which nulls the session and drops the Set-Cookie. So a fourth path exists: lift join_google out of null_session, let it establish a session and hand back a live token, and let the card post straight out. It is cheaper than rewriting the validation phase — but it fights the two reasons that action is cookie-free (the page is service-worker cached and is routinely framed by a third party, where a SameSite=Lax cookie is not sent), so it is a narrowing of option 3, not an escape from it.

    Deleting the page (option 3 on board E) means hand-writing a replacement for a global security hook that also guards creator sign-in. It is reachable and it is not first. Note also a fourth job the page does that its own header does not mention: return redirect_to you_path if player_signed_in? — which is where P3's data loss lives, and which anything removing the page would have to re-home.

  7. 7
    The 26-locale obligation, and what is already paid for.

    New UI strings go in en.yml plus the other 24 hand-written files, then bin/rails i18n:en_us regenerates en-US.yml; LocaleEnUsTest fails if it is stale. Put the new keys under you.*, which is already covered by locale_structure_parity_test.rb, rather than inventing a namespace. Anything JavaScript reads has to go through window.I18N — js: plus the curated slice in _i18n_js.html.erb — or it renders as a raw dotted key.

    Some of it is already paid for, but check before counting on it. Three keys under js.player.* survive from the emailed-link era and are translated in all 26 files: join_sent_title ("Check your inbox"), join_sent_body and join_sent_again ("Send it again"). Two of the three reuse verbatim — the title and the resend label are exactly the words a confirmation banner wants. The third does not: join_sent_body reads "We've sent a link to %{email}. It signs you in and keeps this Verto — no password needed", which describes the sign-in link this flow no longer sends. It needs new words in all 26, so count it as new. None of the three is referenced in the JS any more, so they are dead keys being revived rather than shared.

    For a session with no ANTHROPIC_API_KEY, bin/rails i18n:translate takes PRINT= / TRANSLATIONS=. Expect +N lines, 0 deletions per file; a deletion means stop.

    One thing that has bitten before: a new mailer namespace has to be added to NAMESPACES in test/lib/locale_respondent_parity_test.rb in the same commit that creates it. That file's own header records that forgetting it hid an English-only feature for three pushes.

  8. 8
    The respondents already in this state.

    One query before shipping, because it decides whether a second piece of work exists: Player.where(email_verified_at: nil).where.not(password_digest: nil).count. Every one of those is an account that was promised mail and cannot receive it.

    If it is small, do nothing — the banner on /you catches them the next time they visit. If it is large, a one-off mail-out is a separate, gated change with its own rate shaping, not something to bolt onto this push: sending to thousands of addresses that have never received mail from us is exactly how a domain lands on a suppression list.

  9. 9
    What this deck does not do.

    One thing it does unlock, and the code says so itself. /you/account refuses to let a respondent change their address, and gives the reason in as many words: doing so "would need the same proof-of-inbox the sign-in link gives — which is the thing this page cannot send". After §1 it can. The email-change flow is not in this deck and is not costed in the table, but it stops being blocked, and that comment becomes false and has to be rewritten with the rest.

    It does not gate anything (§3). It does not touch the Service Worker, so no CACHE_VERSION bump is needed — the rule is that content and markup reach respondents on the next ordinary online visit, and only a change to the worker's own behaviour needs the bump. It does not change cached_play_page. It does not build the creator-facing "24 waiting on confirmation" panel that board D sketches — that is real and it is costed below, but it is a different surface. And it does not merge the verification mail with a sign-in link: they expire differently, prove different things, and one of them is a credential.

  10. 10
    The test surface, and one guard that would quietly stop guarding.

    These flows carry roughly 96 integration, unit and mailer tests across 7 files, plus ~31 browser tests across 3 system files. There are no fixture YAMLs anywhere in the repo — every test builds its own Organisation, Survey and Player inline with SecureRandom-suffixed slugs, so a new test copies that shape rather than adding a fixture.

    The seven: join_prompt (19), player_claims (21), player_google_join (20), player_password_sign_in (12), player_sign_in (10), player_sign_in_mailer (7), player_oauth_handoff (7). The three browser files are the expensive ones, since the system suite is the ~5-minute half of the gate: end_screen_layout (20), password_visibility (7), end_screen_contrast (4).

    The trap. test/integration/player_claims_test.rb guards the "join sends no mail" property with assert_no_difference -> { ActionMailer::Base.deliveries.size }. The test environment uses the :test queue adapter, so a deliver_later mail never touches deliveries — that assertion would go on passing while the behaviour it describes was reversed. It has to become assert_enqueued_emails in the same commit, or the suite will report green about a fact that is no longer true. The sibling assertion on PlayerSignInLink.last.origin needs the same read.

    Auto-submitting the interstitial (§6) is mostly additive against player_google_join_test.rb's 20 tests rather than destructive: "the bounce page offers the button" still holds because the button stays, and "the bounce page spends nothing" still holds because the handoff is consumed at the callback either way. What it needs is three new ones — it fires on a first view, it does not fire on a back_forward navigation, and it does not fire when the handoff has expired (the page renders "That took a moment too long" and there is nothing to submit). That last one is the easiest to get wrong.

  11. 11
    The lever that would quietly become a mail-bomb amplifier.

    This is the one thing in the deck that is not optional, and it is the reason P1's risk is not "low". PLAYER_JOIN_RATE_LIMIT_SCALE was added on 14 September so a room of 250 people on one venue NAT could all make accounts. Its own comment says exactly why that was safe: the caps "were sized against a threat that no longer exists… it doesn't send mail and hasn't since the emailed-link era", and "that is why the per-IP half of them can be scaled for a crowd, which a mail-bomb guard could not be."

    Sending a confirmation from #join falsifies that sentence. It turns a documented non-mailing endpoint back into a write primitive against a stranger's inbox, and one env var — clamped at (1, 10_000) — into the multiplier on how many strangers one IP may write to. MAX_JOIN_ADDRESSES_PER_IP is 30 × SCALE per hour per published Verto; at the default that is 30 inboxes an hour, and at an event setting it is not.

    What bounds it on the other side, and should be stated in the code: the mail fires on exactly two of #join's branches — a genuinely new Player, and an adoptable shell being given a password. It must not fire when an existing account authenticates, when the answer is use_google, or when the password is wrong. So a stranger's address can be mailed once for an account that did not exist, and never again by the same route once it does; the exposure is first-contact only, which is what makes an unscaled per-IP counter sufficient rather than a per-mailbox one.

    The fix is small and it has to ship with P1: bound the mail on its own counter at the unscaled number. The lever's job is to let a crowd create accounts; it was never a statement about how much mail one address may send. Creating an account and mailing a stranger are different acts and want different bounds.

    And the prose has to move with the code, which in this repo is not a nicety. Two comments become false the moment this ships and both have to be rewritten in the same commit. player_controller.rb's rate-limit header says, in as many words, "An earlier version of this comment justified all of that as protection for an inbox — join 'SENDS MAIL to an address a stranger typed'. It does not" — a comment that already records being wrong once about exactly this. And the paragraph under it, which concludes "that is also why the per-IP half of them can be scaled for a room full of people, which a mail-bomb guard could not be", is the reasoning the new counter exists to replace. Leaving either standing would hand the next reader a justification for widening the very cap that now guards an inbox.

    And there is no feedback loop to catch it going wrong. EmailSuppression::REASONS declares hard_bounce and complaint, but nothing in the app ever writes them — record! is called only from the two unsubscribe controllers, always with "unsubscribe", and there is no ESP webhook route anywhere. So a send at join-card volume to addresses nobody has proved would bounce into silence, with no mechanism to stop trying. That is an argument for the unscaled counter, not against the feature — but it should be a known gap rather than a discovered one.

    A second comment joins the list above: db/migrate/…_create_players.rb says of the column, "Until then the address is unproven, and nothing may be sent to it beyond the sign-in link itself." That file already carries one claim this repo has since falsified; a second should be corrected in the same commit rather than left to accumulate.

    Two more facts worth having while sizing that counter. The per-address bounds — join_email at 5/20min and MAX_JOIN_PER_ADDRESS at 5/hour — key on the exact lowercased string, so v.ictim+1@gmail.com and victim@gmail.com are different budgets and the same mailbox. And code_budget_ok? keys include @survey.id, so "5 per address per hour" is five per published Verto per hour. Neither is a flaw today, because nothing is being sent; both become the shape of the exposure the moment something is.

What it costs, and when it is live

Sized against e29cb2d (14 Sep) — the whole respondent-Google feature, 60 files and 1,931 insertions including two migrations and 26 locale files, built and shipped in one session. That is the yardstick this repo actually moves at. Every row includes its own bin/gate run: five checks, ~7½ minutes, and roughly a one-in-three chance of losing the race to another session and re-running. A green push to Main deploys itself — CI builds the image, the deploy job moves :main and POSTs Render's hook — so "live" is the push, not a separate release.

Deliberately not in this plan

  • Gating anything on confirmation. §3. The consequence and the remedy are already the same thing.
  • Making /play/:token per-session so its CSRF token is live. The shared cache is a large share of a journey's CPU; trading it for one tap is paying in the thing that carries a venue full of respondents.
  • Allowing GET on the OmniAuth request phase. The config is global — it would re-open creator sign-in to the cross-site initiation class OmniAuth 2.0 closed.
  • Merging the verification mail into the sign-in link. Different expiries, different proofs, and one of the two is a bearer credential.
  • A bulk mail-out to existing unverified respondents, until §8's count is known. It is a separate change with its own rate shaping.
  • Re-running a red CI job. House rule: a red Main is fixed with a new commit, never a re-run.
